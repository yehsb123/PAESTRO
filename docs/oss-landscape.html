PAESTRO — 유사 오픈소스 지형 & 비교표

작성 2026-09-20 · 목적: 우리 것과 겹치는 OSS를 파악하고 “빌릴 것 / 지킬 것”을 정한다 · 조사 단계(구현 전)

PAESTRO는 “뜻으로 도구를 고르는 시맨틱 라우터 + 오케스트레이터”이며 접점은 VS Code 확장이다. 2026년 이 분야는 MCP 표준으로 정리되며 세 갈래의 OSS가 형성됐다 — 시맨틱 라우터형, 검색전략 연구, 게이트웨이형. 아래는 각 대표 프로젝트와 PAESTRO의 대조다.

1. 시맨틱 라우터란

도구가 수백~수천 개면 정의를 전부 프롬프트에 넣을 수 없다(에이전트당 도구 상한 128개, 토큰 폭증). 시맨틱 라우터는 도구 설명을 벡터로 색인해 두고, 요구가 오면 의미가 가까운 것만 검색해 꺼낸다. 예: OmniMCP은 도구 58개(≈55K 토큰)를 노출하는 대신 단일 semantic_router 도구(≈500 토큰)만 두고 나머지는 런타임 검색으로 찾는다. PAESTRO의 ③검색 계층이 이것이며, 우리는 한국어 하이브리드 리콜까지 얹었다.

3. 빌릴 것 vs 지킬 것

빌려온다(커스터마이징)

  • 검색 전략 — ScaleMCP TDWA / ToolShed enriched-doc를 우리 하이브리드 리콜에 접목. 지금의 수동 overlay 34개를 이 방법론으로 전체(1,955개)로 확장.
  • auth·정책·로깅 — MCP 게이트웨이(ContextForge 등) 패턴을 엔진 뒤에 두어 ⑤안전을 재발명하지 않음.
  • 단일 진입 라우터 발상 — OmniMCP의 “도구 1개만 노출” 구조를 확장/엔진 계약에 참고.

우리 것으로 지킨다(차별점)

  • VS Code 확장 = 인터페이스 — 경쟁 OSS는 게이트웨이/CLI형. 에디터 안에서 지휘하는 건 우리뿐.
  • 4런타임 통합 매니페스트(vscode+mcp+rest+cli) — 경쟁작 대부분 MCP 전용.
  • 한국어 우선 하이브리드 검색(이번 튜닝: 음차·구절 리콜) + 오프라인 의존성0 툴체인.
  • side_effects 승인 게이트가 검색·오케스트레이션과 한 몸.

4. 전략적 관찰

MCP가 표준이 됐고(2025-11 스펙에 Tasks·OAuth 2.1·중앙 레지스트리 추가), 초기 3,000+ 서버가 등록돼 있다(우리 이미 크롤 중). 게이트웨이형 OSS가 auth·정책을 성숙시키는 중이므로, PAESTRO는 이를 직접 만들기보다 “MCP 레지스트리 위에 얹는 한국어 시맨틱 라우터 + 에디터 인터페이스”로 포지셔닝하면 우리 강점만 남기고 나머지는 OSS에 위임할 수 있다.
